# 探索物品与共享药物规则

背包已接入队员选择。选择物品与当前队员后，可按物品类型执行装备、修炼或服药；界面显示该人物的生命、内力、两件装备和修炼物，不合资格时禁用人物使用按钮并给出原因。原有“对面前的物件使用”入口继续调用场景物品事件，两种用途分别由角色规则和剧情事件处理。

## 数据与入口

物品使用直接修改当前 `GameSession` 的 `PartyState`、物品占用表和共享背包。装备或进入战斗不会复制出另一套人物或库存；原始 `ItemDefinition` 保持只读。物品仍使用原版记录 ID 和 95 个 word 的映射，不按名称重新编号，也不复制原版文件来生成某个人物或某场战斗的物品包。

探索 API 位于 `src/Game.Core/Session/GameSession.Items.cs`，参数中的人物编号是角色 ID：

| API | 行为 |
|---|---|
| `GetItemUseTargets(itemId, mode)` | 按当前队伍顺序返回 `ItemUseTarget(RoleId, Name, Eligible, Reason)`，包括不合资格的人物及原因。 |
| `EquipItem(itemId, roleId)` | 检查装备资格并更新双向占用，不消耗数量。 |
| `PracticeItem(itemId, roleId, confirmTransfer=false, confirmCastration=false)` | 检查修炼资格，必要时要求确认，再更新修炼关系。 |
| `ConsumeItem(itemId, roleId)` | 给所选队员自服药物，使用共享药效和随机序列。 |

`ItemUseMode`、`ItemUseTarget` 和 `ExplorationItemUseResult` 位于 `JinYong.Core.Items`。结果状态为 `Applied`、`Unchanged`、`Rejected`、`ConfirmTransfer`、`ConfirmCastration`；只有前两项的 `Success` 为真，`Unchanged` 不表示实际消耗或修改。

上述动作要求稳定自由行动状态、当前队员、正数量库存和完整物品定义，并保留原物品菜单 `ShowIntroduction == 1` 的入口条件。事件、战斗、切图、未完成的到达处理及已废弃会话不能执行探索使用。战斗用药走战斗动作 API，与探索复用药效；详见[战斗说明](battles.md)。

## 装备与修炼资格

`ItemEligibilityRules` 按原版有符号 word 解释需求，依据 `sub_2BD8B`，没有套用 OpenLegend 后续 NG+ 数值规则。

- 角色内力属性或物品要求任一为 `2` 即通配；否则必须相等。
- `OnlySuitableRole == -1` 表示不限定人物，其余值必须等于角色 ID。
- 当前内力、攻击、轻功、用毒、医疗、解毒、拳、剑、刀、特殊、暗器共十一项均须达到需求；使用当前内力，不是最大内力。
- `NeedIq >= 0` 是资质下限；负数是绝对值上限，等号均允许。例如 `60` 要求资质不少于 60，`-60` 要求资质不多于 60。
- 修炼物品 78、93 对性别字段恰为 `1` 的角色先判不适合；随后扫描十个武功编号。任一槽与物品 `MagicId` 相等，会把此前所有资格失败重新覆盖为适合，包括属性、限定人物及该性别门。这是原机执行顺序，不能改成首个失败即返回。扫描按编号相等进行，不额外添加正编号门槛。

修炼 caller 还先检查武功容量：物品 `MagicId != -1`、第十槽编号严格大于零、且没有相同武功时拒绝。原版检查末槽，没有改成统计十槽是否全部占满。药品自服没有装备、修炼的这些需求门。

## 占用、确认与数量

装备有两个槽：物品 `EquipmentType == 0` 使用第一槽，其余有符号值均使用第二槽。换装先解除该物品原使用者的对应槽，再解除目标原装备的反向占用，最后写目标槽和 `Party.ItemUsers`。装备增益由战斗、状态等读取方合成，不把物品加成永久加进角色基础攻防；背包中的装备数量保持不变。

修炼物品已有使用者时，返回 `ConfirmTransfer`，包括重新选择同一个使用者的情况。Godot 先弹确认，再继续调用；物品 78、93 对性别字段为 `0` 的角色还会返回 `ConfirmCastration`。第二次确认通过才写性别 `2`。拒绝确认、资格不满足或容量不足，都不会先修改性别、经验或占用。

实际换人时，旧修炼者的修炼物设为 `-1`、修炼经验清零，制造经验保留；目标原修炼物解除占用，目标绑定新物品，并清零目标修炼经验及制造经验。同一使用者最终不重新绑定，也不清这两项经验。修炼物品不从背包消失，不能把“绑定”实现成消耗一本秘籍。

探索自服先计算效果；只有共享结果 `HasEffect` 为真时才扣一件，并提交药效。数量归零后移除对应的正数量背包记录与该物品 ID 标记，其他独立的原版 ID 标记保留。无效果时返回 `Unchanged`，不消耗物品。战斗的行动结束与敌方携物消耗由战斗 caller 单独处理。背包沿用当前正数量字典的规范化，未重建 DOS 的全部 200 槽重复 ID、陈旧数量与异常压紧行为。

## 共享药效与原版边界

探索自服和战斗用药都调用 `Items.ItemUseRules.Calculate(actor, target, item, random)`；计算不写角色，返回目标候选字段、23 项原显示增量及实际变化字段。`Apply` 只提交发生变化的字段，避免覆盖已经修改的携带物或其他无关字段。随机数由会话既有事件随机流提供，规则内部不创建另一个随机源。

原版药物规则依据 `sub_2B483` 的历史机器合同：正生命效果按物品原值、随机数和伤势减半项计算；不按最大生命比例放大。相关中间写入保留 16 位回绕，最大生命、最大内力采用原版 999 上限，体力、伤势、中毒各按对应原门槛处理。十三项能力和带毒攻击保留原 word 算术。物品道德与左右互搏两项在原机只进入显示增量，没有写回角色；`HasEffect` 也按这组原显示增量判断，不能用“角色最终是否变化”替换。

OpenLegend 当前 C++ 已有 NG+ 的宽数值、比例放大和毒溢出替换；本项目采用证据中明确标注的原版合同，未把这些后续规则带入。Godot 在角色操作完成后显示结果，没有逐帧复刻 DOS 效果面板的 present、等待与延后提交过程。

## 存档与证据

现有[存读档](persistence.md)继续保存共享库存、物品 ID 集合、`Party.ItemUsers`、人物两件装备、修炼物、相关经验与随机状态。读档恢复这些运行字段，不重新应用装备加成、不重新消耗药品，也不复制物品定义或原版资源。数据定义和资源库身份验证仍由中央资源库负责，见[资源库](resource-library.md)。

静态来源为只读参考工程 OpenLegend 的 `research/evidence/functions/Z_DAT/`：

| 证据文件 | 本阶段采用的合同 |
|---|---|
| `0x2BD8B.md` | 内力属性通配、十一项下限、正负资质、限定人物、已学武功最终覆盖。 |
| `0x2A86C.md` | 物品类型分派、双向换装、练功容量和确认、经验清理、有效药物才消耗。 |
| `0x2B483.md` | 原版药效、条件随机、word 算术、显示增量与写回差异。 |

这些是研究来源路径，独立项目不要求邻居工程存在。合成测试覆盖资格边界、换装、练功确认和经验写集、共享药效与消耗；明确准备过人物及背包的 UI smoke 覆盖背包操作、战斗支援与物品使用。它们不表示完整原版流程、全部 AI 策略或全部内容扩展均已验收，也不是 DOS 运行时逐帧差分。
